# 5.8 Giving-flow — design scoping

Captures the founder rulings + current-state baseline that the next-turn
planning session will author the canonical Gift schema, the scenario-versioning
spec, and the entity/relationship sketch against. Documentation only; no
source-file changes accompany this commit.

---

## 1. FT rulings (recorded verbatim)

**#1 Canonical entity / consolidation:** Ratify Gifts-first. The canonical
Gift = Shape-3 structural spine (explicit giverPersonId; real recipientOrgId +
recipientOrgName; ISO date; sourceSurface) MERGED WITH Shape-2 display reality
(notes retained). GiveScreen session writes FEED the canonical store (resolves
intake-gifts-join: YES). The three diverged shapes consolidate into this one
canonical Gift.

**#2 Modeler scenarios:** Persisted + lightly versioned. Scenarios become a
net-new entity, not ephemeral scratch. Minimal versioning sufficient for
modeled-vs-actual comparison over time.

**#3 Flow directionality:** Any-entry graph (follows from #1). Surfaces
read/write shared Gift + Scenario entities; "Plan" is a lens, not a parent.
GiveScreen-first entry IS in v1 scope.

### Three-way divergence

- **ID scheme — 3 forms.** Seed: `'g-001'` (slug). Session-born: `'g-' +
  Date.now()`. Unified: `'gift-individual-g-001'` (namespaced). Shape 2 mixes
  two forms in one array depending on origin.
- **Date format — 3 forms.** Seed: `'March 12, 2026'` (full English M D, Y).
  Session-born: `'Apr 23'` (short M D, **no year**). Unified: `'2026-03-12'`
  (ISO). `parseGiftDate` (`adapters/individual.js:77-90`) regex requires the
  full-English-with-year form; it would return `{iso: null, parsed: false}`
  on both `'Apr 23'` and `'2026-03-12'`.
- **Org field — renamed.** Shapes 1 & 2 carry `org: string`. Shape 3 carries
  `recipientOrgName: string` plus a structural FK `recipientOrgId` (currently
  always `null` for individual-source records — deferred).
- **`notes` — Shape 2 only,** session-born only. Lost in normalization to
  Shape 3 because the seed (which the adapter actually reads) doesn't carry
  the field.

### Highest-cost consumers to migrate

1. **`src/surfaces/individual/IndividualSurface.jsx`** — `IndividualHome` route
   and its inline `GiftRow` subcomponent at `:584-628`. ~10 direct `gifts.*`
   references (length/slice/Set/total/orgCount derivations) + 6 per-record
   field accesses inside `GiftRow`. The `GiftRow` is currently file-scoped to
   Home.
2. **`src/surfaces/individual/History.jsx`** — deepest derivation (the

   the CPA copy-text builder that string-formats `g.org`). Fewer raw sites

## 3. Parker hard lines (invariants)

These must survive into any schema draft.

- **The canonical Gift is a donor-DECLARED record with at most an "exported to
  CPA" marker. NO payment/execution/settlement/transfer-lifecycle field,
  ever.** Confirmed: none of the 26 fields across the three current shapes
  carries such state — recording the gift IS the only state. StewardHouse
  does not custody or execute payment (CLAUDE.md §7 Path B).
- **GivingModeler is a structural canvas the donor builds — never a
  recommender, optimizer, or rate/rank engine.** Shape and persistence of
  Scenario records must not introduce a scoring, ranking, or "suggested
  allocation" axis.

## 4. Carried debt

To be absorbed by the persistence/schema pass, not fixed in flight.

- **Budget-literal mismatch.** `individualProfile.js:27` carries `'$1K–$10K'`
  (no spaces); `intakeData.js:30` BUDGETS array and `GivingModeler.jsx:7`
  `BUDGET_TO_DEFAULT` keys both carry `'$1K – $10K'` (spaces). For the
  canonical demo user the modeler's lookup is dead and falls through to its
  `5000` default. Same numeric outcome by accident.
- **Gift IDs use `Date.now()`** (`GiveScreen.jsx:63`). Should move to
  `crypto.randomUUID()` per Enterprise QA #97 precedent (Enterprise's session
  ID at `EnterpriseCompliance.jsx:20`). Same submit button is also not
  disabled in-flight, so a fast double-click could land twice.
- **Date-format unification, target ISO.** The three formats above collapse
  to one. `parseGiftDate`'s English-month regex either generalizes or retires.

## 5. Schema half (planning-session output — opening input to the persistence pass)

### 5a. Canonical Gift field set (12 fields)

Unified structural spine + session display reality, donor-declared, ISO dates,
explicit giver FK. Consolidates the three current shapes into one.

- `id` — namespaced (`gift-individual-{n}` lineage); `crypto.randomUUID()` for
  new writes (carried `Date.now()` debt). Replaces all three id schemes.
- `giverPersonId` — explicit FK. The field accounts make non-optional (only
  unified had it).
- `recipientOrgId` — FK to the org directory, **NULLABLE BY DESIGN** (write-in
  gifts to orgs not yet in the directory have no FK). A reference, never an
  evaluation hook (recipient-FK seam — Morgan).
- `recipientOrgName` — denormalized display string, always present (what
  Home/History read today as `org`); carried even when `recipientOrgId` is
  `null`.
- `amount` — number, USD. Consistent across all three shapes already.
- `date` — ISO `YYYY-MM-DD`. Resolves the 3-format divergence; `parseGiftDate`
  retires in favor of ISO-native.
- `type` — `unrestricted | directed`. Donor-declared structure.
- `vehicle` — `personal | daf | community`. Donor-declared.
- `recurring` — boolean.
- `notes` — string, optional. Shape-2 display-reality field retained per
  ruling; CPA export will plausibly want it.
- `sourceSurface` — `'individual'` literal for now; the namespace keeping
  unified multi-source.
- `exportedToCpa` — **Parker's ONLY permitted lifecycle-adjacent field.**
  Records a DONOR ACTION (export to CPA), never a MONEY STATE (no
  settled/cleared/pending). **HARD CEILING**: this is the only field in this
  family that may ever exist. Schema-level enforcement: the Gift table's
  field list is closed and documented; no payment/execution/settlement/
  transfer column, ever.

Flat shape by design — no nested structure, no status enum, nothing inviting
a payment lifecycle.

### 5b. Scenario entity — versioning spec (snapshot floor)

Net-new entity (Modeler is a pure sandbox today). Floored at
snapshot-not-history.

A Scenario is a labeled, timestamped snapshot of modeler inputs — NOT an edit
log.

- `id` — `scenario-{uuid}`.
- `ownerPersonId` — giver FK (same as Gift).
- `label` — donor/advisor-authored string ("Conservative 2026", "If the
  catalog sells").
- `createdAt` — ISO timestamp. THIS is the version axis: multiple snapshots
  ordered by creation time, comparable against actuals.
- `inputs` — the six modeler knobs frozen: `annual`, `years`, `growth`,
  `grantPct`, `careerOn`, `careerRate`.
- `derivedAtSnapshot` — optional cached `{finalFund, totalIn, totalOut}` so a
  list view doesn't recompute trajectories; makes modeled-vs-actual a single
  read.

Deliberately NOT: no per-edit diff, no undo stack, no field-level history.
"Lightly versioned" = save several named snapshots, see them side by side over
time. Parker guardrail as schema constraint: `inputs` carries NO
"recommended"/"suggested" field; `derivedAtSnapshot` carries NO rank/score
axis. Describes what the donor BUILT, never what the platform ADVISES.

### 5c. Entity/relationship sketch

```
Person (existing, unified)
  └─ giverPersonId ──< Gift          (one person, many gifts)
  └─ ownerPersonId ──< Scenario      (one person, many scenarios)

Organization (existing directory)
  └─ recipientOrgId ──< Gift         (nullable: write-in gifts have no FK)

Gift   — atomic donor-declared record (the 12 fields above)
Scenario — labeled modeler snapshot (the spec above)

Plan = a VIEW, not a table. A derived lens over (this Person's Gifts +
       their declared intake answers + optionally a selected Scenario).
       No Plan row exists; "Plan" is a query.
```

**Pre-answers** (gated items resolved by structure):

- `intake-gifts-join`: **YES.** GiveScreen writes a Gift with
  `sourceSurface:'individual'` straight into the canonical store. No separate
  session-gifts bag. The unified projection becomes the live store (stops
  being a dead-end).
- `individualProfile`-raw-vs-unified: resolves toward unified. The Person
  record IS the account-backed identity; Gift/Scenario hang off its FK.
  `individualProfile` becomes demo-user seed data, not a parallel truth.
- `Plan`-as-view confirms any-entry directionality (ruling #3): every surface
  reads/writes the same two tables; Plan / GiveScreen / Modeler are each just
  a lens.

### 5d. OPEN RULING (FT) — `GiftRow` extract-or-migrate

Blast radius named `IndividualSurface.jsx` (Home + inline `GiftRow`) the
highest-cost migration. When the canonical Gift lands, `GiftRow` either
(a) migrates in place with Home, or (b) extracts to a shared primitive Home +
a future unified consumer reuse. #116-class call (InteractiveCard sibling),
BUT distinct: #116 had 3 consumers and no cross-surface need; `GiftRow` is
about to gain a real second consumer (anything reading the canonical Gift) —
the exact "revisit when genuinely cross-surface" condition #116 named.
Planning lean: **EXTRACT**. NOT a blocker — deferrable to the migration slice
when scoped. FT to rule then.
